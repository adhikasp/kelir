## 2. Highest-value improvements to kelir's prompt, loop and tool surface

Ranked by value/effort. "Evidence" is an event seq from the implementer transcript (seq = the
`tool_started`/`tool_settled` seq for a call, `assistant` seq for reasoning) or an exact diff/notes
line. "Change" names the file and the exact text/shape to add.

**F1 — `edit`: show a short context snippet on `old` misses; make `replace_all` counts actionable.**
Value high / effort low. Evidence: 15/82 `edit` calls failed; 8 "`old` not found" (seq 732, 772,
790, 1355, 1495, 1775, 2005), 3 ambiguous matches (1440, 1445, 1670), 1 "`edits` must be an
array" (1620), and a *partial* multi-hunk apply that reported "2 applied" of 3 (seq 845) —
transcript seq 1512: "the 2 it reported 'applied' were different from what I expected due to
ordered hunks". The model spent several repair steps re-reading the file after each miss.
Change: in `src/tools/edit.rs:216–224`, for "`old` not found" include the first 80 chars of
`old`, the file's line count, and up to 3 best fuzzy candidate lines (`strsim` already in the tree;
otherwise a cheap prefix match) with a note "re-read the exact text with `sed -n`"; for ambiguous
matches, echo the matched lines with their line numbers. For `edits`, include the 1-based index
and a `path` in every error (the current prefix only says `change 3 of 5`). Document in the `edit`
tool description (`src/tools/mod.rs:210`): "`edits` hunks are applied in list order against the
updated text; errors name the hunk index; re-read after a partial failure".

**F2 — Guard against silent collateral damage from an edit (brace/import/statement loss).**
Value high / effort medium. Evidence: at least five repairs for lines removed by an over-broad
`old`: seq 1407 (closing brace of `slug`), 1427 (`pub mod child;` replaced by `pub mod channel;`),
1457 (Duration import), 1652 (`let mut body`), 1707 (`let dir`); assistant seq 1382 "The comment
edit accidentally removed a line. Fix it." Change: extend `edit` with an optional
`expect_lines: [substring, ...]` field that must remain in the file after the edit (or a
`dry_run: true` that returns the resulting diff line count without writing). Add to the prompt
(`src/prompt.md`, after the `edit` bullet at line 6–8): "For multi-line `old` on a large Rust file,
check the diff with `git diff -- <path>` at the next read boundary; a removed brace/import is the
most expensive failure here." Cheap half: land only the prompt sentence now.

**F3 — Take the file's current text from the tool result instead of re-reading whole regions.**
Value high / effort medium. Evidence: 188 of 363 `bash` commands contain `sed -n` and 188 contain
`head`; `src/tools/edit.rs:75` already returns "edited <path>: …" but not the surrounding text.
Change: add an optional `context: N` to `edit` that returns `N` lines around each applied hunk
(default 0 to keep output small), so an ambiguous next hunk needs no extra `bash` round trip.
Also add a `view_range(path, from, to)` tool or a `bash` convenience `kelir lines <path> <from> <to>`
only if measurement shows re-reads dominate; the measured median tool gap was 5 ms, so the win is
model steps (447), not wall latency. Prefer the lower-cost `context` field first.

**F4 — Channel: wire `ctl status` to the driver snapshot and fix the `read_status` path split.**
Value high / effort low (this is a real Build 6 defect, not just ergonomics). Evidence: writer
`src/channel.rs:1036–1046` → `state/channel-status/status.json`; reader `src/channel.rs:581–587`
→ `state/channel-status.json`, zero callers; `docs/reference/channels.md:53` promises the former.
Change: point `read_status` at `state/channel-status/status.json`; add a `channel` object to the
session `Status` response in `src/session.rs:2460–2492` using `crate::channel::read_status(&state)`
(only when present, never the counts of a different process); assert in `tests/e2e_m10.rs` that
`--status-once` prints non-zero `queue_depth`/`spool_backlog` after an inbound message and that
the file matches. Also make `--status-once` print the *live* snapshot after the first turn (or
rename the flag to `--status-once-at-start` in `src/cli.rs:317–319` + generated docs).

**F5 — Channel: close the kill -9 acceptance gap with a restart e2e at the reply→done boundary.**
Value high / effort medium. Evidence: `docs/retros/m10-impl-notes.md` "Kill -9 at all five crash
points is covered at the spool level by unit tests … the e2e suite does not kill the driver at
each point" and transcript assistant seq 2127/2132 (a proposed case that did not land). The fake
server already records `duplicate` per reply id (`tests/support/channel_server.py:113–121`), so the
assertion is free. Change: extend `tests/e2e_m10.rs` with a helper that spawns the driver, injects
a message, waits for one reply line in `replies.jsonl`, kills the child by exact PID with
`kill_on_drop`/TreeGuard, relaunches with the same state dir, and asserts (a) no second reply for
the same id, (b) the spool has no unfinished record after the restarted process drains. Add two
more points if cheap: kill after spool write-but-before claim (inject while driver is stopped), and
kill mid-turn (abort a scripted SSE stream) then assert replay. Keep the global spawn cap: the
implementer's transcript seq 2017/2032 records that 3 concurrent real-process drivers timed out,
which is why the scenarios are sequential (`tests/e2e_m10.rs:265–269`) — do not parallelise them.

**F6 — Channel: make idempotency real at the kelir boundary, not a hint to the bridge.**
Value high / effort high (the implementer's third stated gap). Evidence: `docs/DEVIATIONS.md`
"At-most-once reply with a server-side idempotency key … A bridge that ignores it can still get a
second reply"; `src/channel.rs:728–752` sends `message_id` and trusts the server; `src/channel.rs:1103`
sends the reply *before* `done` at `1116`. Change (two-stage): (1) add a local `channel-replies.jsonl`
append-only ledger keyed by message id, fsync'd immediately before the reply call, and have the
replay path skip any id already in the ledger; (2) add a configurable `reply_idempotency =
"assume" | "verify"` (`src/mcp/config.rs` + `src/config.rs` + generated tables) where `verify`
asks the bridge for a receipt (a `reply_result` field / `message_id` echo before `done` is
written) and leaves the spool unfinished with a logged unknown outcome if no receipt arrives. This
converts "silent duplicate" into "logged unknown", matching the brief's "otherwise at-most-once
with a logged unknown outcome".

**F7 — Channel: distinguish fallback classes instead of one generic string.**
Value medium / effort low. Evidence: `src/channel.rs:56–62` defines four fallback constants; only
`DEFAULT_FALLBACK` can ever be used (`src/channel.rs:1098–1102`); transcript assistant seq 2002
shows a 500 being classified as `turn paused`, which the model recognised as semantically wrong.
Change: match `Outcome::Failed(reason)` on the session's `turn_ended.outcome` (the event already
carries `reason`, `docs/reference/events.md:32`): `steps`/`cap` → paused text, timeout → timeout
text, `provider` errors → default, `Outcome::Gated` → gated text and **no reply to the remote user
at all** unless `channel_fallback_on_gate = true` (new config key in `src/config.rs` + tables).
Add a unit test for `outcome()` on three synthetic event slices (`turn_ended done/paused/deny gate`)
and an e2e for the gate case (the brief lists it, currently missing).

**F8 — Brief availability: make the milestone task file part of the branch, and make the prompt
say what to do when it is absent.**
Value medium / effort low. Evidence: assistant seq 19/44/49 — "The brief file `docs/tasks/M10.md`
doesn't exist yet … exists in git history on another branch … read it from that commit"; the
compaction summary at seq 780 repeats it. The model spent steps 4–10 hunting for the task.
Change: land `docs/tasks/M10.md` with the job branch (or a pointer file `docs/tasks/README.md`
mapping milestone → commit), and add to `src/prompt.md` after the "Plan once" bullet: "If your brief
is missing from the working tree, check the base commit before searching other branches; say in
your notes which commit supplied it." This is a one-line prompt change with no tool work.

**F9 — Emit a machine-readable terminal status line for headless `kelir channel` (and for
`kelir run` gates).**
Value medium / effort low. Evidence: the run ended with a text-only `final_text` at seq 2234 and
the report script's `--if working` guard refused because the orchestrator was idle; assistant seq
2222/2227 records using a raw `hc send` fallback. `docs/SPEC.md:331` mentions OSC status, but a
headless driver has no Herdr pane to read it. Change: on `kelir channel` shutdown print one NDJSON
line `{"event":"driver_stopped","answered":N,"replies":N,"fallbacks":N,"backlog":{...}}` to
stdout (alongside `--status-once`); have `report-to-orchestrator.sh` fall back to a file marker
plus a plain `hc send` unconditionally when the guard declines (it already does the latter, so
only document it in the `delegation` skill and `docs/reference/channels.md`).

**F10 — Keep the prompt's read-budget rule measurable; add a "compact before 150K" hint.**
Value medium / effort low. Evidence: seq 776 `warning prompt_tokens=150787` and seq 780
`compacted`, after 97.6% cache hits and 73K avg prompt post-compaction; `docs/retros/FINDINGS.md`
already asks for `compact_at_tokens = 150000`. The prompt has a "no big cat" rule (`src/prompt.md:14–17`)
that the model followed (only 9 `cat` calls), but nothing about compaction cadence. Change: add to
`src/prompt.md`: "If the session warns about prompt size, call `compact` with a focus containing
the task, the exact file:line map and outstanding gaps; do not keep reading large files into a
warm window." (Optionally add the `compact_at_tokens` config key from FINDINGS; that is a separate
config/gate change.)
