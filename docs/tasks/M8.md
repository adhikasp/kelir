# M8 — gates (six events) and the builtin skills `delegation` and `herdr`

Prereq: M7 spec decisions known (children are CLI processes). Read SPEC *Gates: where every opinion lives*, *Subagents* (delegation is a builtin skill, not a tool),
*Herdr awareness* (the `herdr` skill), *Sources, skills and memory*, the M8 milestone row, docs/reference/README.md, STEER-7's trust model (gates run as child processes of
the session: they receive event JSON on stdin and must not receive the session token or any secret in env/argv beyond what is intended).

## Build
1. **Gate runner**: an executable run at six named events (`session_start`, `prompt_submit`, `before_tool`, `after_tool`, `turn_end`, `session_end`), allow / deny / rewrite
   per the SPEC table; declared three equivalent ways: `[gates]` in config.toml, a skill's `scripts/` file bound with `metadata: {kelir-gate: <event>}`, or an inline
   command string. Event JSON on stdin (with session dir and log path), decision JSON on stdout `{"decision":"allow|deny|rewrite","reason":"…","input":{…}}`.
   **Timeout 30 s; a gate that crashes, times out or prints garbage is logged and treated as allow (fail open).** `turn_end` deny continues the turn once with the reason
   as a message and **blocks at most once per turn**. Every run is a `gate` event (`gate`, `event`, `decision`, `reason`, `ms`, `rewritten?`, `error?`).
   MCP calls are gated as tool `mcp:<server>.<tool>`. Windows and Unix process handling (hidden console, process-tree kill on timeout, no leaked processes, `.cmd`/`.ps1`
   gates via the configured shell). The gate's environment is scrubbed (no provider keys, no session token; document exactly what it gets).
2. **`observe`** lists what fired (gate events) and the effective gate configuration (without secrets).
3. **Shipped example gates** (generic, under `examples/gates/`, no private names, documented in docs/reference/gates.md): `verify-before-claim` (turn_end: blocks a hedged final
   answer such as "probably/I think/from memory" when no check ran that turn, once), `note-check` (after_tool on edit: runs a user-supplied checker over the edited file),
   `git-sync` (session_start pull / session_end commit and push, opt-in, never force), `numbered-answers` (prompt_submit: resolves "do 1,4" against the last numbered list in the
   log). They are examples users copy; nothing is enabled by default.
4. **Builtin skills** (Agent Skills format, embedded in the binary like the `kelir` skill, listed by the sources code, injectable by the hint): `delegation` (when and how to start
   children with `kelir run --child` / `kelir brief`, caps, foreground vs background, what to put in the task, reading results) and `herdr` (inside a Herdr pane: `hc ls --json`
   state/status/agent/name/where/cwd across machines, group `where` by space prefix to count agents sharing my space, `hc get/read/send/wait`, `hc machine ls`, and the rule
   never kill another agent's pane; outside Herdr the skill says so). Keep them short; they point at `kelir docs` topics for depth.
5. Docs: SPEC Gates section reconciled with what was built (DEVIATIONS), docs/reference/gates.md (+ config keys, events, env of gates), drift test passes.

## Tests (pyramid)
Unit: decision parsing (allow/deny/rewrite/garbage/empty/huge), fail-open paths, once-per-turn block counter, event JSON shape, env scrubbing, gate binding via skill metadata.
E2E (mock): each of the six events fires; a crashing gate fails open; a timing-out gate fails open within the timeout and its tree is killed; a hedged final answer is blocked once
and the turn continues; rewrite of a tool input; deny of a tool call returns `denied by gate <name>: <reason>`; `observe` lists what fired; real-process tests with the Drop-guard
harness (no leaks, no windows). Live drive: a real cheap-model session with the example gates enabled.
