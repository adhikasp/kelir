# M9 — named sessions, jobs, single-flight, STATUS

Milestone row: "jobs, named sessions, `STATUS` | a job resumes its session the next day; single-flight holds". Goal: kelir can be run by a scheduler (cron, a
systemd timer, Windows Task Scheduler, any external trigger) as a recurring job that keeps its context across runs, never overlaps itself, and leaves a human- and
machine-readable status. kelir has no daemon and no scheduler of its own: the job command is what the scheduler invokes.

## Build
1. **Named sessions**: `kelir run --name <name> ...` creates a session and records `names/<name>` -> session id in the state dir (atomic write; names are `[a-z0-9._-]{1,64}`);
   `kelir run --name <name>` on an existing name RESUMES that session (M3 resume) and appends the new task as a user message (`from: job`); `kelir sessions ls [--json]` lists
   sessions with name, state, last activity, cost; `kelir sessions rename|forget <name>`. A name collision with a live session is refused with the holder's pid.
2. **Jobs**: `kelir job run <name>` runs the job defined in `jobs.toml` (config dir, then project `.kelir/jobs.toml`): `[jobs.<name>] task = "..."` or `task_file = "..."`, optional
   `provider`/`model`, `max_steps`, `timeout` (wall clock for the run: on expiry the turn is stopped, the outcome recorded, exit code 124), `session = "<name>"` (default the job name,
   so every run resumes the same named session), `new_session_every = "7d"|"never"` (start a fresh session when the old one is older or its context is large; carry the old session's
   summary as a source), `notify` hooks (a command run on done/error/timeout with the job name, outcome and STATUS path in its environment; gate-like: scrubbed environment, 30 s timeout,
   never changes the exit code).
3. **Single-flight**: a job never overlaps itself. One lock per job (`jobs/<name>/lock`) taken atomically with owner pid + process start time + command; taken over only when the holder is
   provably gone (pid-reuse safe; follow the lessons in docs/reviews/buildinfra-review.md and scripts/gate-lock.sh: atomic create-and-own so an ownerless lock is never observed, no stealing
   of a fresh lock, release only by the holder). A second `kelir job run <name>` exits 75 immediately (`--wait <secs>` waits) and appends a `skipped` record to the job's history, never a
   second concurrent turn. A crashed holder frees the lock. Works on Windows and Unix.
4. **STATUS**: `jobs/<name>/STATUS.json` (machine) and `STATUS.md` (human, short) written atomically at run start and end: job, session id and name, run id, started/finished, outcome
   (`done|error|stopped|timeout|skipped|paused`), steps, tokens, cost (STEER-8 numbers), cache hit ratio, the first lines of the final answer, last error, and a `schedule` string the job
   declares for humans (kelir does not schedule). `kelir job status [name] [--json]` prints it; `kelir job history <name>` lists the last N runs (append-only `jobs/<name>/runs.jsonl`).
   The job's model can read its STATUS and a `notes/` dir through bash: tell it the paths with ONE source line when run under `kelir job run` (not by growing the base prompt).
5. **Resume the next day**: the system prompt is frozen at session start (it holds the date, never the time); on a resume across a date change append a tail `source` message ("it is now
   <date>") so the model knows without touching the cached prefix. Compaction keeps working across runs. Exit codes: 0 done, 1 error, 2 usage, 75 skipped, 124 timeout.
6. Docs: a SPEC section (Jobs) reconciled with the code, docs/reference (jobs.md, config, cli, files, events), a recipe for cron / a systemd timer / Windows Task Scheduler in
   docs/reference/jobs.md (generic names only), drift test passes. STEER-7 trust: session/job verbs need the token like any state-changing verb; `names/` and `jobs/` are owner-only.

## Tests (pyramid)
Unit: name validation, the lock state machine (pid reuse, ownerless, stale, fresh), STATUS atomic write/read, duration parsing, the new_session_every rule, the date-change source.
E2E (mock): a job run twice resumes the same session and the second request's prefix is a strict extension of the first (cache); a simulated next day (inject the date) adds the date source
and nothing else; two concurrent `job run` (real processes): exactly one runs, the other exits 75; kill -9 of the holder frees the lock; the timeout stops the turn and exits 124 with a
tree kill; the notify hook runs with a scrubbed environment; `sessions ls`; corrupted STATUS/names are tolerated. Real-process tests use the Drop-guard harness and a process-count
watchdog (an incident: about 1000 runaway sh.exe from a sibling job's tests); no leaked processes, no console windows. Live drive: a real cheap-model job run twice with the real binary.
