# M10 — channel mode: chat bridges through MCP, a durable spool, fallback replies

Milestone row: "Telegram: a bridge through `kelir mcp`, `notifications/claude/channel` inbound, `turn_done`, kelir as a third harness behind a router | a DM topic gets an answer
and a fallback reply; the spool survives a restart". The public repo ships the generic mechanism; a concrete chat bridge (Telegram or anything else) is just an MCP server
configured with `channel = true` in config.toml, outside this repo. Verify with a fake channel server shipped under tests/support. A real bridge needs the maintainer's credentials
and infrastructure: that part is a decision/credential only he can supply (report it at the end, do not guess tokens).

## Build
1. **Channel protocol (document it in SPEC + docs/reference/channels.md)**: a channel server (an MCP server with `channel = true`, connected at session start per M6) sends inbound
   chat messages as MCP notifications `notifications/claude/channel` (payload: message id, conversation id, sender display name, text, optional attachments (file paths or data),
   reply-to); kelir answers with a tool call on the same server (configurable tool name, default `reply`, args: conversation id, text, optional reply-to) and sends a `turn_done`
   notification/tool call when a turn ends (so the bridge can stop a typing indicator). Capability negotiation: kelir declares the channel capability the server needs to start
   sending (decide from the MCP spec of the server you test with, make it configurable `[servers.x] declare_capabilities = [...]`); kelir never declares a permission-relay capability
   (it has no approvals). Unknown/oversized/malformed notifications are dropped and logged once.
2. **`kelir channel` (long-running, headless)**: starts the configured channel servers and serves conversations: one **named session per conversation** (M9 names:
   `chan-<server>-<conversation>`; resume across restarts), **single-flight per conversation** (a second message while a turn runs is queued as a `later` message and delivered at the next
   boundary or turn end, never a concurrent turn), bounded concurrency across conversations (config `max_active`, default 4; the rest wait), per-conversation and global rate limits.
3. **Durable spool**: every inbound message is appended (fsync) to `spool/<server>.jsonl` BEFORE it is acknowledged or processed; processing marks it `claimed` then `done`
   (append-only records); on restart/crash unfinished messages are replayed exactly-once-ish (at-least-once delivery + dedupe by message id; a turn that already logged the user event for
   that message id is not re-run). The spool is size-bounded with compaction of done records. Kill -9 at any of: after spool write, after user event, mid-turn, after the final answer before
   the reply is sent, after the reply: tests assert no loss and no duplicate reply (a reply is idempotent by message id where the server supports it, otherwise at-most-once with a logged
   unknown outcome, never a silent drop).
4. **Fallback reply**: if a turn ends in error/paused/timeout, or the provider is unavailable beyond the retry budget (STEER-5), send one short fallback reply to the conversation
   (configurable text) and record it; never reply twice for one inbound message; a stop requested by the user in chat (`/stop`) maps to the `stop` verb.
5. **Envelope and trust**: the inbound text arrives as a user message with `from: channel` and an envelope header naming server, conversation and sender (the model knows it is talking
   to a remote chat user, not the operator); attachments follow the M5-B/TUI v2 rules (stored under the session dir, pointer in the prompt, `kelir view` for images). STEER-7: no secret
   from config.toml `env` in any log; a channel message cannot invoke state-changing session verbs; the channel path is not a way around gates (M8 `prompt_submit` gates run on inbound text).
6. Herdr status for `kelir channel` (one OSC status for the process: working while any turn runs, idle otherwise) and `ctl status` showing conversations, queue depth, spool backlog.
7. Docs: SPEC section reconciled with the code (DEVIATIONS), docs/reference (channels.md, config, cli, events, files), drift test passes.

## Tests (pyramid)
Unit: spool append/claim/done/replay/dedupe, per-conversation queueing state machine, rate limiter, envelope rendering, notification parsing (valid, malformed, oversized, unknown fields).
E2E (mock provider + fake channel MCP server): inbound -> answer -> reply; a second message during a turn is queued and delivered, not concurrent; two conversations in parallel (bounded);
provider failure -> exactly one fallback reply; kill -9 at each of the five points then restart: no loss, no duplicate; flood of 1000 messages stays bounded; `/stop` works; a gate denies an
inbound prompt; no secret canary in events/spool/logs; real-process tests use the Drop-guard harness and a process-count watchdog (an incident: about 1000 runaway sh.exe from a
sibling job); no leaked processes, no visible console windows. Live drive: a real cheap-model conversation through the fake server.
